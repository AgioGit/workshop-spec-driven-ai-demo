# Feature Scaffold Process — Walkthrough

> This document captures the real interaction used to scaffold PBI 002 (`add_mock_data`).
> Use it as a worked example to understand the feature scaffold workflow.

---

## 1. The initial prompt

The user invoked the scaffold skill with the following instruction:

> *"Use the skill tool to invoke the 'feature-scaffold' skill, then follow the skill's instructions to help with:*
> *002 add_mock_data @src\Presentation.Api\Program.cs*
> *- Task 1: Move mock data in to .json formatted files in a data folder*
> *- Task 2: Generate and expand mock data size*
> *- Task 3: Come up with relevant other mock data entities"*

The tagged file (`Program.cs`) was attached so the agent could read the current seed data inline.

---

## 2. What the skill did

### Step 1 — Explore the codebase

The agent read:
- `src/Presentation.Api/Program.cs` — to understand the existing inline seed block (3 Equipment rows, 2 hardcoded `LocationId` GUIDs)
- `docs/features/001_get_equipment/specification.md` — to calibrate document structure and style
- `docs/features/README.md` — to understand the existing feature registry

### Step 2 — Determine feature parameters

From the prompt and the tagged file, the agent derived:

| Parameter | Value |
|---|---|
| `id` | `002` |
| `name` | `add_mock_data` |
| `type` | `refactoring` (moving and expanding existing code, no new behaviour) |
| `description` | Move mock data from `Program.cs` into JSON files, expand data size, add new mock entities |

### Step 3 — Create the feature folder and files

The agent created `docs/features/002_add_mock_data/` with four files:

| File | Purpose |
|---|---|
| `specification.md` | Full pre-filled spec describing scope, current state, target state, and testing requirements |
| `plan.md` | Stub — to be generated by the `/feature-plan` skill |
| `implementation.md` | Stub — to be generated by the `/feature-implementation-doc` skill after tests pass |
| `code-review.md` | Stub — to be generated by the `/code-review` skill before merge |

The agent also appended a new entry to `docs/features/README.md` to register the feature.

---

## 3. How the specification was written

The skill's `refactoring` template was used as the skeleton. The agent filled it in using:

- **Current state** — derived directly from reading `Program.cs` (the hardcoded seed block)
- **Target state** — driven by the three tasks in the prompt:
  - Task 1 → `data/*.json` file layout with format examples
  - Task 2 → Data volume targets table (15 equipment, 4 locations, 10 operators, etc.)
  - Task 3 → Scope table listing the domain entities to add (`Location`, `Operator`, `Booking`, `MaintenanceEvent`)
- **Breaking changes table** — the agent noted that existing GUIDs must be preserved to avoid breaking existing tests or API calls

One section was initially left as a `<!-- TODO -->`:

> *Add integration test that verifies seed count if one does not already exist*

---

## 4. Refining the spec — human input

After the scaffold was created, the user indicated they wanted the integration tests included (not just noted as a future TODO):

> *"For the TODO, I want to add the integration tests also."*

The agent updated the testing requirements section to read:

- Existing `dotnet test` suite must pass unchanged after the refactor
- Manually verify the API returns data after startup (curl `/get-equipment`)
- **Add an integration test that seeds the in-memory DB from the JSON files and asserts the correct record counts per entity**

This turned the TODO into a concrete, committed requirement.

---

## 5. Key takeaways for other users

| Lesson | Why it matters |
|---|---|
| **Tag the relevant source file** | Attaching `@Program.cs` let the agent read the actual code rather than guess at the current state |
| **Use tasks, not vague descriptions** | Numbered tasks (Task 1, 2, 3) gave the agent concrete, verifiable objectives |
| **Review TODOs after scaffolding** | The agent marks uncertain decisions as `<!-- TODO -->`. Review them immediately and resolve them — each TODO left open is a decision the planner will make for you |
| **Iterate via follow-up messages** | You don't have to get everything right in one prompt. The user added integration tests in a one-line follow-up, and the agent updated only the affected line |
| **Spec → Plan → Implement → Review** | The four files enforce a workflow. Don't skip to implementation before the spec is complete |

---

## 6. Next step

With the specification complete and all TODOs resolved, the next step is:

```
/feature-plan
```

This reads `specification.md` and generates a detailed, phase-by-phase `plan.md` ready for implementation.
